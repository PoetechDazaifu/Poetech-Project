## P0 — データモデル・検索契約を正規化する

### 背景

元データの`在住地`（詳細な住所情報）と`場所`（公開用の居住地分類）が混同されていた。さらに、複数AIタグが一つの文字列として保存され、タグ検索が部分一致だった。

### 完了条件

- `residence`と`location_category`を別カラムで保存する。
- タグを区切り文字に依存せず個別の完全一致タグとして保存・検索できる。
- 検索APIはページネーション、入力検証、総件数を返す。
- 詳細な在住地を公開API・画面に出さない。
- 自動テストでタグ正規化と検索契約を検証する。

### 状態

実装・自動テスト済み。

## P1 — 検索の高速化と絞り込みUIを改善する

### 背景

本文・データ元検索は先頭ワイルドカードの`LIKE`であり、データ増加時に性能低下する。UIのデータ元候補は固定値で、実データの揺れを吸収できない。

### 完了条件

- SQLite FTS5等で本文検索を高速化し、検索仕様（部分一致・表記ゆれ）を文書化する。
- データ元・タグ・居住地分類の候補と件数をAPIから取得する。
- UIで候補を動的に表示し、フィルター解除と検索中状態を一貫して扱う。
- 検索性能と検索結果の回帰テストを追加する。

## P1 — ワードクラウド生成をキャッシュ可能にする

### 背景

同じ検索条件でも都度PNGを生成しており、CPUと応答時間を浪費する。

### 完了条件

- 正規化済み検索条件をキーに結果PNGをキャッシュする。
- TTL・容量上限・データ更新時の無効化方針を定義する。
- 同一条件でキャッシュヒットすることを自動テストする。
- 生成失敗時の利用者向けメッセージとサーバーログを整備する。

## P1 — フロントエンドを静的資産へ整理しアクセシビリティを改善する

### 背景

HTMLテンプレート内のCSS/JavaScriptと`static/`配下の古い資産が重複している。検索結果はスクリーンリーダーへ適切に通知されない。

### 完了条件

- CSSとJavaScriptを単一の静的資産として管理し、未使用資産を削除する。
- 検索結果・エラー・ローディングにARIA live regionを設定する。
- キーボード操作だけでフィルターの選択・解除・追加表示ができる。
- XSSを防ぐDOM生成を維持する。

## P2 — データ取り込みを検証可能なパイプラインにする

### 背景

Excel取り込みは変換しか行わず、必須列、件数、未分類タグ、重複句の異常を検出できない。

### 完了条件

- 変換前に必須列・空欄・重複・未知タグを検査し、機械可読なレポートを出す。
- 変換、検証、DB再構築を単一コマンドで実行できる。
- 入力データのバージョン・更新日をDBに記録する。
- 失敗時に既存DBを破壊しない原子的な再構築にする。

## P2 — CI・コンテナ・依存関係を保守可能にする

### 背景

テストをローカルでしか実行しておらず、依存関係の再現性とコンテナの更新方針がない。

### 完了条件

- GitHub ActionsでDB構築、ユニットテスト、構文・依存関係チェックを実行する。
- 対応中のPythonバージョンと依存関係の固定方針を明記する。
- Dockerイメージのアーキテクチャ固定を見直し、ヘルスチェックをデプロイ設定へ反映する。
- `gunicorn`など未使用依存を残さない。

## P3 — 本番運用の可観測性・防御を追加する

### 背景

正常性監視、アクセス傾向、レート制限、ブラウザ向けセキュリティヘッダーの運用方針がない。

### 完了条件

- `/healthz`を監視対象に設定する。
- CSP、`X-Content-Type-Options`等のヘッダーとCDN外部資産の利用方針を定める。
- ワードクラウドAPIへのレート制限またはキャッシュ前提の保護を導入する。
- 個人情報・アクセスログの保存期間と公開方針をREADMEに記載する。

## P3 — Cloudflare導入の段階計画を決める

### 背景

現在のPython画像生成をWorkersへ全面移植するのは適さない一方、CDN・独自ドメイン・WAFは有効である。

### 完了条件

- Render継続+Cloudflare前段化、検索APIのD1移行、全面移行の比較を作成する。
- 選定基準（アクセス量、コスト、運用負荷、画像生成性能）を合意する。
- 採用する構成とロールバック手順を文書化する。
